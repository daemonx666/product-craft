# Spec：一句话需求 → 规格文档 → 开发

AI 写代码时最大的浪费是猜错需求：做完才发现范围不对、漏了关键规则。这个 skill 在写代码前用少量精准的问题把关键决定问清楚，落成一个文件。之后无论是这次会话、新会话还是另一个 agent（Claude Code / Codex），都能从这个文件接着做。

保持轻量：一次对话内完成，问题少而准，文档写到够用为止。

## 设计原则：长在现有项目上

新功能要在项目已有的东西上生长，而不是另起一套。用户要的是“这个项目里的这个功能”，不是一个通用方案；凭空设计出来的东西往往和现有数据、界面、习惯对不上，返工成本最高。

- 优先扩展现有模块，复用现有的数据结构、接口、组件、工具函数和命名习惯。
- 交互和视觉跟项目里已有的同类界面保持一致。
- 需要新建一套东西、或者要改变现有功能的行为时，在文档里写明理由，并把它作为问题问用户。
- 对标产品只用来提供选项和启发；它的做法和项目现状冲突时，以项目现状为准。

## 流程

### 1. 读项目和相关功能（不用问用户）

有针对性地读，不要通读整个代码库：

- README、CLAUDE.md / AGENTS.md、依赖清单（package.json、go.mod、pyproject.toml、Cargo.toml 等）
- docs/ 和已有的规格（docs/specs/ 等），沿用项目已有的文档习惯
- 顶层目录结构、最近约 20 条 git log
- 用需求里的关键词搜索相关代码，找出会被这个需求影响或复用的模块

对直接相关的功能要读深一些，读到能说清这三件事为止：**数据怎么存**（模型、字段、存储位置）、**流程怎么走**（入口、主要调用链）、**界面用了什么**（页面、组件、样式习惯）。不相关的部分不用读。

给用户一段简短的现状说明：项目是什么、给谁用、技术栈；相关功能现在怎么工作；这个需求打算复用、扩展还是修改哪些部分。如果是空项目或定位读不出来，就把“项目定位”作为第一个问题。

### 2. 找对标

找 2～4 个有这个功能的同类产品或开源项目，优先找和本项目定位相同的（比如项目是微信小游戏，就找同类小游戏里的同类功能，而不是泛泛的大厂产品）。能联网就搜，不能就凭已有知识，并注明“未联网核实”。

每个对标写一两行：它怎么做的、哪些值得借鉴、哪些不适合我们（包括和项目现状不兼容的地方）。最后一句话结论。

对标放在提问之前，是为了让后面的问题能给出有真实参照的选项（“像 A 那样…… / 像 B 那样……”），用户回答起来更快、更准。

### 3. 一次一个问题

- 每次只问一个问题，给 2～4 个选项，第一个是推荐项并附一句理由，用户也可以自由回答。Claude Code 里有 AskUserQuestion 工具就用它；Codex 等环境用带编号的纯文本选项。
- 只问从项目和对标里推断不出来、并且会改变做法的问题。代码里已经有答案的（比如现有的分页方式、权限模型），直接沿用，不要再问。选项要基于现状来给，例如“沿用现有的 X / 在 X 上加一个字段 / 新建 Y”。按影响大小排序：目标与用户 → 核心场景/主流程 → 范围（首版做什么、不做什么）→ 关键规则与数据 → 界面交互 → 异常与边界 → 验收标准。
- 一般 3～8 个问题。剩下的不确定点都有合理默认值时就停，把这些默认值记为“假设”。
- 用户随时说“按推荐”“你定”，就对剩下的问题全部采用推荐项，并记为假设。

### 4. 写规格文档

- 路径：`docs/specs/<YYYY-MM-DD>-<slug>.md`，slug 用英文短横线。项目已有规格目录（如 specs/、.kiro/specs/）就沿用。
- 按 [references/spec-template.md](references/spec-template.md) 的结构写。正文用用户的语言，标识符和路径用英文。
- 让 AI 好读的几个要点：
  - 每条需求编号（FR-1、FR-2），后续任务和讨论能直接引用。
  - 验收标准要能验证，写成 Given / When / Then 或具体的可检查条件。
  - 明确写出“不做什么”，这比写“做什么”更能防止范围膨胀。
  - 写清现状：相关功能现在怎么工作，新需求和它们是什么关系。
  - 技术方案落到具体文件和模块，分成复用、修改、新增三类，一眼能看出改动有多大。
  - 不写宣传语和空话；没有内容的章节写“无”或删掉。
- 篇幅够用就好，小功能一页左右。

### 5. 确认

告诉用户文档路径、3～5 行摘要，以及列出的假设，问是开始开发还是先调整。确认之前不写实现代码，因为文档的价值就在于便宜地纠正猜错的地方。确认后把 frontmatter 的 status 改成 confirmed。

### 6. 开发

- 按文档里的“任务拆分”顺序做，每完成一项就在文档里勾掉（`- [x]`），status 改成 in-progress。这样中途断了，新会话读文件就能接着做。
- 开发中发现需求要变，就先改文档并写进“变更记录”，不要让代码和文档悄悄分叉。
- 做完后逐条对照验收标准自查，向用户报告每条的结果（通过 / 未通过 / 没法验证），status 改成 done。

## 续做

用户说“继续 spec”，或者项目里有 status 为 confirmed / in-progress 的规格时：读那份文档，从第一个没勾的任务继续。有多份进行中的规格，就先问用户继续哪一份。
